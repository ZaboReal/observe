How their product works, per the docs

  1. A script tag (or a managed Cloudflare Zaraz install) loads the SDK with an sf_pk_ publishable key and starts an anonymous session.
  2. The SDK batches behaviour to /v1/sdk/events. Evidence and scoring stay on their servers.
  3. client.identify({userId, accountId}) labels the session (unverified). The backend can attach verified identity with POST /v1/identify.
  4. When the user starts a protected action, the page sends an opaque, signed, expiring session token to your backend. Forms tagged data-switchfrog get it injected as switchfrog_session_token.
  5. Your backend calls POST /v1/verify {actionId, sessionToken} with the sf_sk_ secret key.
  6. The response is {verdict, score}, where the score is fixed per verdict: human = 1, unknown = 50, agent = 99.
  7. Your own code decides what to do. Their example: human → allow, agent → hold for account-owner review (HTTP 202), unknown → deny.

The WebMCP product (“Actions”)

Three capture levels: behavior → requests → schema. At the higher levels the SDK records the structure of same-origin fetch/XHR traffic (methods, paths, query names, JSON property names and types, never values). From that they generate an OpenAPI document (GET /v1/discovery/openapi.json) and multi-step “workflow tools”. The SDK registers these through document.modelContext.registerTool with readOnlyHint, consequentialHint and untrustedContentHint annotations. Any workflow with a non-GET step needs a host-supplied confirm() hook. Tools run as the logged-in user, and the caller is never identified.

Their docs state that, when model refinement is on, path segments and property names may be sent to the OpenAI Responses API. Regulated buyers will object to that.

What to copy and where they are thin

  • Copy: one-tag install, Cloudflare Zaraz and GTM installers, consent bridges for OneTrust, Cookiebot and Sourcepoint, publishable vs secret keys with a 7-day rotation grace, documented retry rules (at most 3 attempts with jittered 250/500 ms waits, 503 only), llms.txt, a docs MCP server and a “set up with a coding agent” prompt.
  • Thin: the verify API returns no driver name, no confidence and no reasons, though the marketing webhook shows driver: "claude-in-chrome", confidence: 0.97.
  • Missing: no signed-agent verification, no user consent, no visa, no hosted policy, no audit log, no cross-site memory and no published accuracy. “Unknown” and every allow/deny rule are left to the customer's code.

6 · The cryptographic passport

Verifying agents that sign their requests

Cloud agents can prove their operator with HTTP Message Signatures (RFC 9421) under the Web Bot Auth profile. Since September 2026 there is a single IETF working-group draft (draft-ietf-webbotauth-httpsig-protocol-00), but deployed agents send two header shapes. Verify at the outermost edge, pass the result to the origin as a header we sign, and let behaviour corroborate. A signature that does not match behaviour raises a spoofing alert.

What arrives

# draft -00 shape (Google-Agent sends this)
Signature-Agent: g="https://agent.bot.goog"
Signature-Input: sig1=("@authority" "signature-agent";key="g");
  created=1791244800;expires=1791248400;
  keyid="<JWK SHA-256 thumbprint>";alg="ed25519";
  tag="web-bot-auth"
Signature: sig1=:<base64 Ed25519 signature>:

# legacy shape ChatGPT still sends: accept, mark "legacy"
Signature-Agent: "https://chatgpt.com"
Signature-Input: sig1=("@authority" "@method" "@path"
  "signature-agent");created=…;expires=…;keyid="…";
  nonce="<64 bytes>";tag="web-bot-auth"

# Visa TAP: different tags, keys from Visa's JWKS
Signature-Input: sig2=("@authority" "@path");…;
  tag="agent-browser-auth"   # or agent-payer-auth

What the edge verifier does

  1. Strip inbound copies of our verdict headers. Accept CDN verdicts only over an authenticated origin path.
  2. Route each signature label by tag: web-bot-auth to Web Bot Auth; agent-browser-auth or agent-payer-auth to Visa TAP (8-minute window, nonce required); a UCP-Agent header to UCP. Anything else is logged as unrecognised.
  3. Parse Signature-Agent as a dictionary or a legacy string. Require @authority or @target-uri, expires − created of 24 h or less, and ±60 s of clock skew.
  4. Fetch /.well-known/http-message-signatures-directory (no redirects, size and time limits, no private IPs). Cache it for 5 min–24 h with ETag, and serve stale keys on error.
  5. Look keys up by the pair (URL, thumbprint we compute ourselves). Never trust the directory's kid: Google's are short strings, not thumbprints.
  6. Rebuild the signature base with the Host the client used and verify. SeatGeek measured 600–900 µs per request.
  7. If a nonce is present, record it until expires. The draft does not require nonces, so missing replay protection lowers assurance for writes.
  8. Emit PC-Passport: <JWS> to the origin. An invalid signature from a known key counts as spoofing, which is worse than no signature. A failed directory fetch is not spoofing.

7 · The differentiator

Issuing a visa, from the first click to the entry log

An agent's first sensitive action triggers a one-time consent prompt shown to the person. The prompt describes the request in product terms, the person approves it with a passkey, and later actions go through without asking until the visa expires or is revoked.

8 · The hard problem

Making a visa stick to an agent that will not say who it is

An in-browser agent shares the person's cookies, IP address and device, so nothing cryptographic separates them. We bind visas at four strengths. Higher rungs give more assurance but need more cooperation from the agent provider, and the strength of the binding sets which scopes a visa may carry.

The B2 handshake, concretely

// 1. our tag, on first agent detection
window.postMessage({ type: "agent-passport/challenge",
  nonce: "q7Z…", origin: location.origin }, "*")

// 2. the agent extension's content script answers,
//    signed with a key in its provider's Web Bot Auth directory
{ type: "agent-passport/present",
  agent: "anthropic/claude-in-chrome", agent_version: "1.14",
  provider_user: "pseud_3f…", origin: "https://app.ledgerline.com",
  nonce: "q7Z…", task_id: "t_81", intent_hash: "sha256:…",
  iat: 1791247440, exp: 1791247500, sig: "…" }

// 3. we verify, upgrade the passport to verified, and set a
//    60-second first-party cookie so CDP-driven navigations carry it

A WebMCP tool (passport.present) can carry the same payload. Content-script postMessage scales better than externally_connectable, which only works for origins named in the extension's manifest.

Tiers mapped to binding

TierMeansHighest scope
HumanNo agent detectedwhatever the role allows

A visa never grants more than the person's own role. For unsigned agents it works as a restriction plus convenience: fewer prompts and no challenges, never extra privilege.

Why a passkey is the anchor

WebAuthn with user verification needs a fingerprint, face or device PIN on the person's own authenticator. An agent driving the page can click the button but cannot pass that check on its own, so a passkey co-sign proves a person intended this specific action.

Visas die on handoff anomalies

If the handoff detector sees a different driver from the one the visa names, or the device changes, the visa is suspended for that session and the next sensitive action falls back to “ask the person”.

Prompt injection limits

A visa limits what a hijacked agent can do, but it cannot tell an instruction from the person apart from one a malicious page planted. Provider defences help without closing the gap: Anthropic reports its mitigations cut Claude in Chrome's attack success rate from 23.6% to 11.2%. Keep consequential scopes behind a per-action passkey, cap volumes, and when an agent strays off task (say, opening SSO settings during a “read reports” job) downgrade the visa to read-only.

9 · Try it

Border decisions: one call, one stamp

Choose who is acting, the state of their visa and the action. The simulator runs the default policy pack, shows the rule that decided, and prints the entry log line. Observe mode computes the same decision without enforcing it, which is how every install starts.

AdmitRun the action and log it.
SlowAdmit at a lower rate; unknown automation starts here.
Request visaShow the consent prompt to the person and tell the agent to wait.
Ask the personHold the action until a passkey co-sign arrives.
ReroutePoint the agent to a cheaper WebMCP tool or API (the fast lane).
BillAdmit and send a meter event to billing.
RefuseBlock, with a reason the agent can relay to the person.

Cedar can only permit or forbid. Each policy carries an @outcome annotation, and /decide returns the strictest outcome among the policies that determined the result: refuse, then ask, then request visa, then slow, then reroute, then bill, then admit. Cedar evaluates in microseconds, so latency comes from loading the session and visa. Keep those in memory with a 30–60 s TTL plus push invalidation. Targets: about 5 ms added at p99 in-process and 25–30 ms for a same-region API call. AWS AgentCore Policy already uses Cedar with a LOG_ONLY mode, a precedent for our observe mode.

Kill switches at three levels: one visa, one passport (an agent instance), or one agent product across a whole tenant, for example “turn off Comet for everyone at Northwind”.

10 · Phase 0, and a marketing asset

The benchmark lab

The biggest risk in the plan is that behavioural detection is not accurate enough to hang visas on, and no vendor publishes a false-positive rate. So the lab comes first: it sets the go/no-go decision, produces training labels, blocks bad model releases, and gives us a public scorecard nobody else has.

Agent matrix (refresh nightly)

Claude in ChromePerplexity CometChatGPT desktop browser + Chrome extensionOpenAI Codex browserGemini in ChromeEdge Copilot ModeChatGPT agent (signed)Google-Agent (signed, partial)Browserbase / Stagehandbrowser-useClaude / OpenAI computer usePlaywright · Puppeteer · Selenium+ humaniser variants

Consumer agents need a prompt typed into their own UI. Script that with OS-level automation on dedicated test machines, and record each agent's version string with every run. The matrix changes fast: OpenAI reportedly shut Atlas down in August 2026 and moved agent browsing into the ChatGPT desktop app, a Chrome extension and a cloud browser.

What we measure and publish

  • Recall at fixed false-positive rates: per agent, at 1%, 0.1% and 0.01% FPR on human sessions, at session and action level. At 0.1%, a site with a million sessions flags 1,000 real people
  • Time to verdict: median actions before the score clears ±3, and the “unknown” rate
  • Handoff error: how far the detected person-to-agent switch is from the true one
  • Driver accuracy: confusion matrix over named agents, including “agent, driver unknown”
  • Calibration: expected calibration error and Brier score
  • Decay: train on version N, test on N+k, monthly
  • Hard humans: FPR reported separately for screen readers, voice control, switch access, IME and dictation, password-manager autofill, Citrix/RDP, Vimium and developers with DevTools open
  • Cost: SDK size and CPU per minute (Vouched publishes 41 KB gzipped, under 5 ms)
Proposed go/no-go for Phase 1: at least 90% recall within 5 actions for the top five in-browser agents, at 0.5% FPR or less on general human sessions and 1% or less on assistive-tech users. Miss it, and the product leads with signed agents and passkey co-sign (B1) until it is met.

What has been published so far

No vendor publishes accuracy or false-positive rates. Five academic papers from 2026 do. Their numbers are near-perfect in the lab, but every human cohort is small or did different tasks from the agents, which is exactly the gap a public benchmark fills.

13 · Filling the gaps

What the current plan is missing

The research doc covers the market and the product idea. These are build and business items it does not cover yet. P0 blocks a launch, P1 blocks the first enterprise deal, P2 can wait.

Detection edge cases

  • Assistive tech (screen readers, voice control, switch access) looks automated; it needs its own FPR budget and an allow path P0
  • Password managers, Grammarly and other extensions that type or paste P0
  • Customers' own QA bots, RPA (UiPath) and synthetic monitoring need allow-listing P1
  • Agents that block the sensor: missing telemetry on a protected action should count as evidence, not as a pass P0
  • Mobile apps, webviews and Electron desktop apps sit outside a JS tag P2

Other channels

  • Agents that skip the UI and use the customer's API or MCP server: the visa should cover OAuth/MCP clients too, or a blocked agent simply moves to the API P1
  • Shared logins and service accounts: one account, many people and agents P1
  • Multi-tab and background-tab sessions; iframes and embedded apps P1

Integration friction

  • Mapping routes to actions is the hardest part of every install. Infer it from HTTP methods, export headers and OpenAPI x-visa-scope tags, learn it in observe mode, and have an admin confirm. Switchfrog's action discovery does this already P0
  • Batch decisions for page UI (which buttons to show an agent) through AuthZEN /evaluations P1
  • Agents' declared intent (a task hash from the handshake) as an off-task anomaly signal, never as authorisation P2

User experience

  • A “that was me” appeal for false positives, which also feeds labels P0
  • Agent-readable refusals (reason and next step) so agents can explain them, not retry in loops P0
  • Consent fatigue: admin pre-approval, plan-level default visas, progressive scopes P1
  • Copy and localisation for prompts written in the customer's voice P2

Security of our own

  • Our SDK is a supply-chain risk on customers' pages: versioned URLs, SRI hashes, a CSP guide and a public changelog P0
  • Token replay: bind session tokens to the session and the action, with short TTLs P0
  • Fail-open vs fail-closed per action; status page; regional failover P1
  • SOC 2 Type II, pen tests, bug bounty P1

Legal & privacy

  • Behavioural telemetry is personal data under GDPR: DPA, purpose limits, retention (e.g. raw events 30 days), CMP integration on day one P0
  • Template terms-of-service language for customers on agent use and visas P1
  • EU AI Act and sector audits: Article 26 has deployers keep logs for at least 6 months, and the Annex III high-risk deadline moved to 2 Dec 2027. Map entry-log fields to SOX, HIPAA and FINRA duties too P1
  • Data residency (EU and US regions) P1
  • End users are the customer's employees: per-person agent reports can count as employee monitoring (German works councils, for example). Offer aggregate-only views P1

Ecosystem & standards

  • Provider BD: pitch the fast lane to Anthropic, OpenAI, Perplexity and Google before building B2 P1
  • Join IETF webbotauth and the W3C WebMCP group; propose the handshake and an agent-declaration signal P2
  • Integrations: Okta, Entra and Auth0 for admin policy; Splunk and Datadog; Stripe and Chargebee for metering P1

Go-to-market

  • A free “agent audit” that installs in a day and gives a shareable report as the land motion P0
  • Pricing metric: monitored active users plus decisions, with an agent-hours meter for billing P1
  • A distinct brand: “passport” and “visa” names are already in use P1
  • A competitive switching kit: SDK shape compatible with Switchfrog's P2

Operating the models

  • Drift alerts when an agent ships a new version (recall drop on a named driver) P0
  • Shadow models and per-site calibration; explainable reason codes P1
  • An on-call rota for detection regressions, like fraud teams run P2
